# 智能旅行助手 · 图集说明

五张图，各回答一个问题。**不要用一张图硬塞五件事**——流程图之所以"一眼能看懂"，
正是因为它只回答"主链路长什么样"。

| 图 | 回答的问题 | 文件 |
|---|---|---|
| **LangGraph 图** | 节点之间什么关系？谁碰模型、谁读写什么、条件分支在哪判定？ | `智能旅行助手-LangGraph图.png` |
| 流程图 | 端到端主链路长什么样？ | `智能旅行助手-流程图.png` |
| 数据流图 DFD | 数据从哪来、在哪被加工、存到哪？ | `智能旅行助手-数据流图.png` |
| 时序图 | 一次请求里谁调谁、什么顺序、各花多久？ | `智能旅行助手-时序图.png` |
| 状态图 | 行程和编辑器会进入哪些状态、靠什么跳转？ | `智能旅行助手-状态图.png` |

> **为什么新增 LangGraph 图**：流程图里原来横排的是"四节点线性图"，那是条件路由之前的样子。
> 加了 `weather → adjust` 之后，那条横排已经过期；而且流程图**讲不清"谁读谁写"**——
> 那才是"多个 agent 怎么交互"的实质答案。所以单独一张图，只讲图本身。

## 0. LangGraph 图（本文最该先看的一张）

**看图时注意**三件事：

1. **颜色代表"是否碰模型"**：橙色只有 `planner`（主图）和 `draft`（重排图）两个，其余全是白色工具节点。
   全流程 **1 次 LLM 调用**——这不是"省 token"，是"把不确定性关进一个格子"。
2. **每个节点标了"写：xxx"**：节点之间没有调用关系，只通过共享状态通信，而且**各自只写自己的字段**
   （`attractions_raw` / `weather_raw` / `hotels_raw` / `routing`）。字段分区是"平级"的技术前提——
   否则"后写覆盖"会让最后跑的那个变成事实上的独裁者。
3. **条件边是虚线的**，旁边写着"分支判定在 `_after_weather()`：纯函数，非模型"。
   这是本项目最重要的一个架构决定：**路由由代码判定，不由模型判定**，所以跑两遍路径一致、可以离线测。

下半部分是**重排子图**：`draft`（调模型 + 守门 + 重试）→ `confirm`（`interrupt()` 停住）→ `apply`。
其中 `confirm` 下面的蓝色框是"人"——它是整个系统里**唯一能否决模型的地方**；
而 `apply` 的注释写着"未选中的天直接取旧对象"，这是**构造上的保证**，不是"相信模型没改"。

右下角两个小标签是这套流程的代价，必须一起讲：`InMemorySaver` + `thread_id` 意味着
**进程重启会话即丢**，所以后端要单 worker 常驻。

## 1. 流程图（主链路）

**看图时注意**：颜色代表"层"，不是装饰。输入 → 前端 → 接口 → 图 → 后处理 → 返回 → 展示 → 存储。
右侧三块绿色是外部服务，箭头指向图里的四个节点，说明"这四步分别依赖谁"。
底部红色虚线是失败分支——四种失败各有确定处置。

**为什么这样画**：把"确定性后处理"单独画成一格，是为了说明**模型只负责它不能替代的那部分**
（预算求和、序号重编、天气重建都不该交给生成）。

## 2. 数据流图 DFD（Level-1）

**看图时注意**：形状本身有语义——圆角框是处理（带编号 1.0~6.0）、直角框是外部实体、
左侧带编号栏的是数据存储（D1 行程、D2 配图缓存）。**每条箭头都必须有数据名**，
没有名字的箭头说明画的人自己也没想清楚传的是什么。

**它揭示的两个设计决定**：

- 行程不是"算完就丢"，而是回到用户手里、由前端触发落盘（5.0 → 6.0）——所以刷新页面还能找回；
- 配图是"查过一次就写盘"（4.0 ↔ D2），因为 Unsplash 的 Demo 配额只有 50 次/小时。

**没画进来的**：静态地图的内存缓存（上限 40 张）。画进来会和 D2 的箭头交叉，反而看不清，
所以在注释里说明。

## 3. 时序图

**看图时注意**：左侧是累计耗时，虚线是回包。**LLM 那一条最重要的信息是宽度和时长**：
它占总时长的七成以上，其余全部加起来不到 5 秒——这解释了"为什么改一次提示词，等待时间就变了"，
也说明优化方向不在工具调用上。

**右下三条失败路径**：空壳重试、模型断连返回 503、补图失败留空。这三条都不是"看情况"，
而是有确定分支——这是这张图想传达的第二个信息。

## 4. 状态图

**看图时注意**：这张图不是为了好看，是为了回答"**每个按钮该在哪个状态可点**"。
它直接对应三条产品约束：

- 保存失败绝不显示「已保存」——状态由请求结果决定，不由"我改过了"决定；
- 生成失败保留表单内容，用户不必重填 7 个字段；
- 工具部分失败但行程可用：进「只读」并展示 errors，不阻断使用。

**为什么有自环**：只读态也允许删景点（方便），但那条边必须配一个"可撤销"——否则删了就找不回来。
这是实际用出来的需求（用户反馈"没点编辑也能删，删了没法恢复"）。

## 关于 ER 图

这个项目**没有 ER 图**，因为存储是 JSON 文件（`data/trips/<id>.json`），没有表结构。

这不是遗漏，是一个被记录下来的设计决定：量级是"几十份行程、单机自用"，
一份 JSON 能直接 `git diff` 看改动，写入用临时文件原子替换即可。
如果以后要多用户、要按条件查询，再换 SQLite —— 那时才需要 ER 图。

**把"为什么没有"写下来，比硬画一张 ER 图更有价值。**

## 生成方式

四张图都是 PIL 手绘（`diagram_kit.py` 提供共用的形状/文字/箭头），不依赖 graphviz 或浏览器：

```bash
python docs/draw_dfd.py
python docs/draw_sequence.py
python docs/draw_state.py
```

流程图脚本在 `docs/draw_flow.py`；LangGraph 图在 `docs/draw_graph.py`（两者共用 `diagram_kit.py`，配色与字号一致）。

**为什么手画**：中文排版可控（字体、换行、对齐）、改一个坐标就能调、不依赖外部工具链。
代价是布局要自己算——所以每张图改完都要**渲染出来用眼睛看一遍**，
这一步抓到过：图例压住方框、标题被箭头穿过、"继续改"指错了框。
